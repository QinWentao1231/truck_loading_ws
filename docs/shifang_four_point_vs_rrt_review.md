# 什邡四点路径与旧 RRT* 的一致性及干涉核查

日期：2026-10-19。范围仅为 `src/sczy_shifang_palletizing`；本次未改动运行程序、协议或参数。

结论：原版垛序可以保持一致，但四点运动路径和避碰效果不等价于旧 RRT*。当前实现存在能够放行的干涉/越界反例，不能作为“已保证无干涉”的版本直接验收。
四点法本身可以用于规则码垛，问题是当前实现没有覆盖完整运动段和侧壁边界。

## 对照依据

- 当前入口：`sczy_shifang_palletizing/runtime.py:118` 调用 `calculate_path`，`:119` 仅依据 `issues` 拦截，`:124` 发送四点报文。
- 当前路径：`rule_planning/path_planner.py:76`，路径固定为 `x0 → x1 → APP → goal`。
- 旧路径：包内保存的 `scripts/backup/20250611/main.py:285` 至 `:430`；另查更早的 `backup/main.py`。这些是源码备份，不能证明现场曾部署的二进制版本。
- 旧 RRT*：`scripts/rrt_planning/rrt_base.py:91` 至 `:126` 和 `scripts/legacy_auxiliary_methods/search_space.py:57`。

| 内容 | 当前四点法 | 保存的 RRT* 版本 |
| --- | --- | --- |
| 箱体放置顺序、分抓、原始方向/目标坐标 | 继承旧垛序；本次样例逐项一致 | 原始垛序 |
| 中间路径 | 按规则直接生成固定四点 | 在局部搜索范围内生成多点路径，尝试绕障 |
| 接近点、起始点 | 新的高度阈值、固定初始 Y、左右间隙偏移 | 按旧代码的箱高/层数、方向和偏移选择；与当前公式不同 |
| 避碰检查 | 前三点的八角点、高度和部分同层间隙 | 搜索边沿八条角点轨迹采样检查，r=1（长度单位 mm） |
| APP 到落点 | 未检查箱体碰撞 | 旧代码也直接追加 goal，不能认为该段曾有完整保证 |
| 机器人连杆/关节/姿态变化 | 无模型和检测 | 同样没有完整机器人模型和检测 |

注意：旧版搜索边的采样函数也不是严格连续几何证明，八角轨迹可能漏掉面内/包含式相交；初始 `x0→x_init`、直接追加的最终落箱段也不等于经过 RRT 检查。
因此本结论不是“旧 RRT 绝对安全”，而是当前版本又失去了搜索边的采样检测和绕障能力。

## 发现 1：中间路径穿过障碍物仍会下发

当前 `path_planner.py:112` 至 `:115` 只遍历 `path[:3]`，不检查三个线段。`goal` 只进入高度检查。
`environment.py:1731` 已有 `trajectory_collision_free`，但本包运行调用链中没有调用它；函数存在不代表已启用。

构造的反例使用现有测试订单的第一抓、当前 planner.json 默认配置，并在环境中加入一个专用测试障碍箱。它不是实测现场订单，也不是声称原垛序会在第一抓之前生成这个障碍。

```text
搬运包围盒（含高度余量）：460 × 500 × 680 mm
x0   = (200, 1200, 1420)
x1   = (200,  225, 1420)
APP  = ( 50,  100,   50)
goal = (  0,    0,    0)

障碍箱真实范围：
X=[0,460]，Y=[200,450]，Z=[750,1330] mm
```

四个端点都不与真实障碍箱重叠；但是在 `x1→APP` 线性运动中，约从段长比例 6.57% 到 98.54% 存在重叠。
例如箱体参考点约为 `(121.168,159.307,700)` 时就与障碍箱重叠。

- 当前 `calculate_path` 返回 `issues=[]`。
- 用内存模拟通信调用真实 `serve_commands`，仍生成并发送一个 180 字节四点报文。
- 对同一条 `x1→APP` 边执行旧 `SearchSpace.collision_free(...,r=1,...)`，返回 False。
  复现时保留原检查方法和采样代码，只把 Rtree 的点查询替换为等价直接 AABB 点查询；没有运行完整随机搜索，也没有断言旧 RRT 一定能找到替代路径。

这说明路径端点检查通过，不能代表运动过程不干涉。

## 发现 2：整抓箱体侧向越界不拦截

`path_helpers.py:96` 至 `:100` 在常见高度区间将 `x0.Y` 固定为 1200 mm。
`calculate_path` 未检查各路径点/线段的 `Y >= 0` 和 `Y+整抓宽度 <= 车宽`。
同文件的 `_check_action_lateral_bounds` 也没有被当前运行流程调用，且其检查对象只是原始落箱范围，不能替代全路径边界检查。

可复现的完整构造订单：车宽 2300 mm，单箱宽 300 mm，每层 7 箱，分两抓 `[4,3]`，剩余间隙分配到两抓之间。
最终箱体总宽 2100 mm，订单可以正常生成，但第一抓宽为 1200 mm：

```text
x0.Y = 1200
整抓右边界 = 1200 + 4×300 = 2400 mm
车厢右边界 = 2300 mm
越界 = 100 mm
当前 issues = []
```

这是按程序自身“箱体位置为最小角、向正 Y 延伸”的模型得到的侧壁越界。
如果现场该过渡点位于车外，需要另外描述车门位置和实际可用空间，不能简单把车内边界一律外推；当前模型没有提供这些信息。

## 发现 3：八角点检查不是箱体相交检查

`path_planner.py:63` 至 `:73` 只判断搬运箱体的八个顶点是否进入障碍物。
例如搬运包围盒 `(0,0,0)→(460,1000,680)` 内包含一个 `(100,100,100)→(200,200,200)` 障碍时，八角点均在障碍外，函数仍返回无障碍。
这个小障碍是几何单元反例，不代表具体现场箱型；它证明该判断无法覆盖完整 AABB 相交。
旧 RRT 的顶点/角点轨迹方法同样有此限制。

## 发现 4：角点补偿规则也不等价

- 旧 `scripts/backup/20250611/main.py:350` 附近允许 dir=2 且宽度差绝对值小于配置阈值时，直接叠加 `dis-rp.W`，包括负值。
- 当前 `path_helpers.py:155` 至 `:162` 只对右半侧、最右抓、dir=2 生效，补偿裁剪到 `[0,40]` mm；测得车宽更窄时不会向内修正。
- 当前补偿仅修改 goal，没有基于补偿后的目标重新验证完整接近/落箱轨迹和侧界。

例如原始车宽 2460 mm、第二层右侧四箱抓原位置 Y=1460 mm：输入距离 2500 mm 时，goal.Y=1500，整抓右边界为 2500 mm，而程序其余路径模型仍使用 rp.W=2460。
若 2500 mm 是准确实测宽度，不能仅据此认定碰墙；但它暴露了名义宽度与补偿后坐标缺少统一边界校验的问题。
反过来，测得宽度比名义值小 30 mm 时，当前不会采用旧版的负补偿，不能假设放置效果仍与旧版相同。

## 已完成的离线验证

可复现脚本：[shifang_path_safety_audit.py](shifang_path_safety_audit.py)。结果：[shifang_path_safety_audit_results.json](shifang_path_safety_audit_results.json)。

```bash
python3 -B docs/shifang_path_safety_audit.py
```

脚本不启动 ROS、不建立机器人或 gRPC 网络连接。

| --- | --- |
| 仓库原有基准订单 | 12 抓通过当前检查；独立线性 AABB 扫掠未发现已放箱体重叠或侧向越界 |
| 207 组构造的规则垛订单 | 与归档原垛序逐项比较一致；检查放行 1279 抓，53 个订单在遇到首次拒绝后停止 |
| 上述放行路径与当前面真实已放箱体的独立扫掠比较 | 未发现重叠 |

| 中间障碍反例 | 当前检查漏过且模拟运行下发；旧边检查拒绝同一条边 |
| 2300 mm 车宽反例 | 起始点整抓越右侧边界 100 mm，当前检查漏过 |
| 包含式相交反例 | 八角点检查漏过 |

207 组为人工构造参数组合，并非 207 份现场订单。每组按当前运行语义遇到 issues 就停止，不把拒绝之后的动作当成已执行。
独立几何核查采用固定姿态轴对齐包围盒沿直线平移的精确区间相交；正常面接触不算穿透。
不包含机械臂连杆、姿态旋转、机器人圆滑插补、实际标定误差或箱体变形。

尝试执行现有完整 unittest 集时，当前系统 Python 缺少 protobuf，导致迁移测试模块不能导入，依赖检查和 gRPC 相关测试也报错；完整套件没有跑通。
本次上述离线脚本不依赖 protobuf，已执行成功；不能把它替代为“所有项目测试通过”。

## 保持四点接口时需要补齐什么

1. 将单点检测改为完整包围盒相交，并对三个运动段做扫掠检测。安全段使用外扩障碍，落箱段使用真实箱体并允许合理表面接触，避免把正常贴箱误判为碰撞。
2. 核对四点及运动过程的车壁、顶部、地面、车门边界；初始 Y 应结合车宽和实际抓宽选择，不能一律固定 1200。
3. 在最终角点补偿之后统一检查落点和接近段，并明确实测宽度与名义宽度的使用规则。
4. 四点候选无解时先拒绝下发，或在四点约束内调整过渡点重新校验。任意绕障不一定能压缩成四点，不能把 RRT 多点结果简单删点后视为同样安全。
5. 对照机器人侧程序确认四点对应 L/J 运动、TCP 和姿态、转角圆滑参数，以及本抓结束到下一抓起点之间的取放/回撤路径。包内未找到 FANUC LS/TP 或机器人 URDF/SRDF，当前 Python 不能证明这些运动无干涉。

已有 `trajectory_collision_free` 可作为接入起点，但其默认 10 mm 离散采样、固定姿态包围盒模型也有边界；不能只加一次调用就宣布现场绝对安全。
以上为整改建议，本次核查未擅自改变现场运行行为。
